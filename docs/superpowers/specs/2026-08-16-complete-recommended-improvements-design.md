# Design: Complete the Recommended Improvements

## Context

`MELHORIAS_RECOMENDADAS.md` records nine improvements identified by the
previous repository audit. Some are already implemented locally, while the
remaining items cover source modularity, quality tooling, documentation
structure, diagram generation, CI hardening, and release automation.

The user explicitly authorized implementing the pending work, updating the
documentation, and merging the result locally and on GitHub. Existing local
changes are part of that authorized work and must be preserved.

## Goals

1. Resolve every item in `MELHORIAS_RECOMENDADAS.md`, including items marked
   partial when the remaining acceptance criteria are clear.
2. Preserve the ForgeLoop public protocol and all existing CLI behavior.
3. Keep the published package free of runtime dependencies. Development-only
   dependencies may be added for linting, coverage, and deterministic Mermaid
   rendering.
4. Make the documentation source-oriented: concise README, a navigable
   documentation index, canonical Mermaid source, and an accessible text
   fallback.
5. Make CI enforce the new quality and supply-chain expectations without
   silently installing tools or weakening existing negative-contract tests.
6. Produce evidence for local verification, GitHub checks, the GitHub merge,
   and local `main` synchronization.

## Non-goals

- Rewriting the Python CI validators into JavaScript. They will be explicitly
  documented as frozen CI-only validators because they protect established
  negative contracts and are not shipped as runtime code.
- Introducing an LLM runtime, orchestration layer, or new ForgeLoop protocol
  state semantics.
- Publishing a new npm package version. The requested publication boundary is
  the GitHub branch/PR merge; npm publication remains a separate release
  action.
- Replacing the existing SVG with an unverified generated asset. The Mermaid
  source and committed SVG must be rendered and compared in CI.

## Design decisions

### Source modularity

Split the three oversized core modules along existing responsibility
boundaries while retaining their current public facade exports:

- `verification-capability.js` becomes a compatibility facade over tokenizer,
  npm classifier, command-resolution, and authority modules.
- `next-action.js` keeps the public `getNextAction` entry point and
  `NEXT_ACTIONS` export while moving model, artifact, and phase helpers into
  focused modules.
- `preflight.js` keeps `evaluatePreflight` and `runPreflight` available while
  moving model, loading, and persistence/consistency helpers into focused
  modules.

No caller should need to change imports. A fixture corpus will exercise real
npm/pnpm/yarn-style argv shapes and assert the same classification contract.

### Declarative CLI dispatch

Keep command metadata in one table containing the command name, handler,
output formatter, and exit-code policy. Parsing and usage generation will
continue to consume the same command allowlist. Special lifecycle commands
may retain small adapters, but `main()` will dispatch through the table rather
than a second hand-maintained if/else chain.

### Quality tooling and dependency boundary

Add ESLint and c8 as development-only tools. Add Mermaid CLI as a
development-only renderer. A dependency-policy script will fail if runtime,
optional, or peer dependencies are introduced and will allow only the
explicitly approved development tools. CI will run `npm ci` before local
commands, so it will never rely on implicit `npx` installation.

Coverage thresholds will be measured against the source tree and recorded in
the documentation. The threshold is a floor for regression detection, not a
claim that every branch is exhaustively tested.

### Documentation and diagram

Reduce `README.md` to orientation, compatibility guarantees, the architecture
diagram, essential blind-run constraints, and links to deeper material. Add a
root `DOCS_INDEX.md` for the full lifecycle, guide catalog, release boundary,
validator policy, and capability notes.

Store the architecture diagram as `docs/forgeloop-flow.mmd`. The existing
committed SVG remains a generated artifact. `npm run docs:flow` renders it
with the local Mermaid CLI, and CI fails if rendering changes the committed
SVG. Keep a text-only fallback in the public documentation.

### Python validators and CI supply chain

Keep the established Python validators in CI, document their frozen CI-only
boundary and invocation, and add regression coverage around that policy.
Add pinned CodeQL, dependency-review, and tag-triggered GitHub release-notes
workflows. Release notes are generated by GitHub CLI after a tag exists; this
does not publish npm artifacts.

## Acceptance criteria

- All nine recommendation entries are marked resolved with evidence and the
  checklist no longer reports pending work.
- Existing Node and Python tests pass, plus lint, coverage, dependency-policy,
  Mermaid, packaging, and generated-artifact checks.
- Public facade exports and CLI behavior remain compatible with the baseline.
- `npm pack --dry-run` includes the intended documentation and source assets,
  but no test fixtures, coverage output, or development-only dependencies.
- GitHub Actions has explicit dependency installation and the new security,
  dependency-review, and release-note workflows use pinned third-party action
  references where applicable.
- ForgeLoop reaches validator-backed completion for the implementation task.
- The feature branch is pushed, the GitHub PR is merged after checks, and
  local `main` is fast-forwarded to the merged remote tip.

## Risks and mitigations

- Generated Mermaid output can vary with renderer versions. Pin the direct
  development dependency through the lockfile, render in CI, and compare the
  generated file.
- Refactoring protocol code can change subtle negative paths. Add focused
  contract tests before moving code and run the complete suite after each
  module group.
- GitHub security checks may expose external-link or platform-specific
  limitations. Report exact statuses and URLs rather than declaring all checks
  green without evidence.
- The repository contains pre-existing local changes. Use explicit staging and
  preserve all related changes; do not reset or recreate the work.
